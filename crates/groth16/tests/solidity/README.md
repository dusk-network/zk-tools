# Groth16 Solidity verifier

This test-only Foundry project exercises circuit-specific Solidity verifiers
generated by `dusk-groth16`. It lives under `tests/` because its generated
contract is an integration fixture, not production source. The contracts call
the BLS12-381 G1 MSM and pairing precompiles
defined by [EIP-2537](https://eips.ethereum.org/EIPS/eip-2537), so they only
work on EVM networks that have activated those precompiles. Ethereum mainnet
has supported them since Pectra.

The verifier ABI is:

```solidity
verifyProof(bytes proof, uint256[] publicInputs) external view returns (bool)
```

`proof` is the 512-byte `(-A, B, C)` transport returned by
`Proof::to_eip2537`; it is not the crate's canonical compressed proof.
`publicInputs` must follow Composer emission order. The generated contract
embeds both the verification key and exact expected input count, so a new
contract must be generated whenever setup produces a new key.
Query points are embedded directly in runtime bytecode. For circuits with many
public inputs, run `forge build --sizes` and check the deployment limit of the
target network.

## Validation boundary

The contract checks the exact proof and public-input counts, requires every
public input to be smaller than the BLS scalar modulus, and rejects identity
proof elements. The EIP-2537 precompiles provide the remaining point
validation:

- G1 MSM validates the embedded public-query points and their subgroup;
- pairing validates every field encoding, curve equation, and subgroup for
  `-A`, `B`, `C`, the computed public-input point, and the fixed verification
  key points;
- failed calls, missing precompiles, and unexpected return lengths all produce
  `false`.

This relies on the target chain implementing EIP-2537 correctly. The contract
does not establish that the embedded verification key came from a trustworthy
setup or that its parameters are algebraically consistent; those remain setup
and key-provenance responsibilities.

`test/fixtures/SquareVerifier.sol` is a deterministic integration fixture. It
is not a production verifier. Regenerate it with:

```console
cargo run --release -p dusk-groth16 --example solidity \
  --no-default-features --features=bls-backend-blst,std -- /tmp/groth16-solidity
```

The example uses a fixed RNG seed strictly so the test artifacts are
reproducible. Never use its key for production. Applications should generate
setup randomness securely, save `VerifyingKey::to_bytes()`, and generate a
contract with:

```console
cargo run --release -p dusk-groth16 --bin dusk-groth16-solidity \
  --no-default-features --features=bls-backend-blst,std -- \
  generate-verifier verifying-key.bin MyCircuitVerifier MyCircuitVerifier.sol
```

Canonical 192-byte proofs can be converted into the verifier's 512-byte
EIP-2537 transport representation with:

```console
cargo run --release -p dusk-groth16 --bin dusk-groth16-solidity \
  --no-default-features --features=bls-backend-blst,std -- \
  encode-proof proof.bin proof.eip2537.bin
```

Run the Solidity suite with `make solidity-test` from the repository root.
Foundry must be recent enough to run tests with the Prague EVM revision. The
suite is dependency-free and exercises a Rust-generated proof plus malformed
and well-formed-but-wrong proofs, incorrect and non-canonical public inputs,
every proof element, field-encoding boundaries, off-curve and wrong-subgroup
points, and ABI length checks. Subgroup cases use the official Ethereum
EIP-2537 failure vectors.
